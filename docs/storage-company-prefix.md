# Общий S3-бакет для нескольких компаний

## Зачем префикс

Каждая компания — своя инсталляция CRM со своей базой. Ключи файлов в бакете
строятся из порядковых номеров этой базы:

| Что | Ключ |
|---|---|
| Договор по сделке | `pdf/contract_deal_12.pdf` |
| Версия документа | `versions/5/v2_5.pdf` |
| Аватар сотрудника | `avatars/users/7/…` |
| Предпросмотр в хранилище | `drive-previews/5.pdf` |

У двух компаний сделка №12 есть у обеих. Без разделения договор одной
перезаписал бы договор другой, а её сотрудники открывали бы чужие документы.
Поэтому каждая инсталляция пишет только под свой префикс:

```
kub/pdf/contract_deal_12.pdf
company2/pdf/contract_deal_12.pdf
```

Префикс задаётся переменной `S3_PREFIX` (или `s3.prefix` в конфиге) и
применяется ко **всем** файлам системы — документам, файлам клиентов,
вложениям чатов, аватарам, хранилищу. Код компании: строчная латиница, цифры
и дефис, до 63 символов. Нельзя использовать имена системных папок (`pdf`,
`drive`, `clients` и т.д.) — приложение не запустится с такой настройкой.

Без `S3_PREFIX` поведение прежнее — всё в корне бакета, а в логе при старте
предупреждение.

## Новая компания

Задать `S3_PREFIX` **с первого дня**, до первой загрузки файла. Переносить
ничего не придётся.

## KUB: перенос уже лежащих файлов

Файлы KUB сейчас лежат в корне бакета. Их нужно переложить в `kub/` до того,
как в бакет начнёт писать вторая компания. Инструмент `s3-company-prefix`
входит в Docker-образ и берёт доступы к S3 из того же `.env.prod`.

Сокращение для команд ниже:

```bash
PREFIX_TOOL="docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm --no-deps --entrypoint s3-company-prefix api"
```

`--no-deps` — чтобы не запускались миграции и зависимые сервисы.

### 1. Выкатить код, ничего не переключая

```bash
make up
```

`S3_PREFIX` пока не задан — поведение не меняется. В логе будет
`WARNING: S3_PREFIX не задан`.

### 2. Посмотреть план

```bash
$PREFIX_TOOL -to kub
```

Ничего не меняет. Покажет, сколько файлов и какого объёма будет перенесено, и
отдельно — что остаётся на месте. Переносятся только системные папки; всё
остальное в корне считается возможно чужим. Если в разделе «Оставлены на
месте» есть папка, которая точно принадлежит KUB, добавьте её:
`-extra-folders имя1,имя2`.

### 3. Скопировать

```bash
$PREFIX_TOOL -to kub -apply
```

Копирование серверное — файлы не проходят через наш сервер. Исходники
остаются, приложение продолжает работать с корнем бакета.

### 4. Переключить приложение

В `.env.prod`:

```bash
S3_PREFIX=kub
```

```bash
make up
```

В логе при старте: `storage: S3 … prefix="kub"`.

### 5. Сразу догнать новые файлы

```bash
$PREFIX_TOOL -to kub -apply
```

Скопирует файлы, загруженные между шагами 3 и 4. Уже скопированные
пропускаются. Шаги 4 и 5 лучше делать подряд и в спокойное время: файл,
загруженный между ними, до шага 5 будет не виден.

### 6. Проверить

Открыть старый договор, фото из карточки клиента, файл в «Хранилище», аватар
сотрудника. Всё должно открываться как раньше.

### 7. Удалить исходники — когда убедились, что всё работает

```bash
$PREFIX_TOOL -to kub -apply -delete-source
```

Исходник удаляется, только если копия на месте и совпадает по размеру.

## Откат

До шага 7 — убрать `S3_PREFIX` и перезапустить: приложение снова читает
корень, исходники на месте. Файлы, загруженные уже после переключения, лежат
только под `kub/` и после отката видны не будут.

## Безопасность

Префикс разделяет файлы компаний на уровне приложения. Если у всех инсталляций
один и тот же ключ доступа к бакету, любая из них технически может прочитать
чужие файлы. Для настоящей изоляции выдайте каждой компании отдельный ключ,
ограниченный её префиксом политикой бакета (`kub/*`, `company2/*`).
